My detector was useless the first time I pointed it at a real attack.

I write small, unglamorous tools and then try to prove they are wrong. The interesting part is never the code; it is what happens when something outside my control gets a vote. More than half the defects I found in this work were in the tests, not the program.

Exhibit -- srcdiff vs. xz-utils

Sixteen false positives, every one shaped like the attack

srcdiff looks for the xz-utils backdoor shape: code shipped in a release tarball that was never in the repository. Every test behind that claim was a four-file toy project with one planted divergence. Then I pointed it at the genuine xz-5.4.5 release against its genuine git tag.

HIGH: code in the artifact that is NOT in the repository
    m4/gettext.m4
    m4/libtool.m4
    m4/lib-link.m4
    m4/ltoptions.m4
    ... 12 more, every one an m4/*.m4

16 HIGH findings, all false  on a release with nothing wrong with it

Every one was an m4/*.m4 file present in the tarball and absent from git. Which is exactly the shape of the attack. The real signal would have been one line in seventeen. That is not a detector; it is noise with an extra row.

Why no allowlist fixes it

build-to-host.m4 is a legitimate gettext macro. It ships in /usr/share/aclocal on any machine with gettext installed. The attacker did not invent a filename -- they shipped a modified copy of a real one, which is why it survived review. Git contained neither version.

The fix was a second oracle. Vendored build machinery comes from the build host, not the repository, so ask the host's own canonical copy instead -- and let the file's in-band version marker decide what a difference means. Different serial means a different upstream release and is expected. Same serial, different bytes means the file claims to be a revision it is not. A file modified in place does not advertise itself as a new release.

16 -> 1

False positives on a clean release, after the redesign. The survivor is a known upstream comment reflow, left in rather than normalised away.

1 in 687

The one false positive is deliberately kept. A rule broad enough to absorb arbitrary comment changes would absorb an injected comment block too.

caught

An injected build-to-host.m4 with its serial intact is reported immediately. The delta between the clean and tampered runs is exactly the injection and nothing else, asserted rather than eyeballed.

Three cases

Things that must refuse

Each of these is judged by something I did not write and cannot influence: the kernel, GNU tar, a published conformance corpus. A test I write to check code I wrote proves only that I was consistent.

srcdiff

supply-chain artifact auditor 473 lines · 25 tests

Reconstructs what a published artifact should contain from its claimed source tag and reports the delta, with findings bucketed by severity. The high bucket is reserved for the xz shape: a legitimate vendored filename whose content does not match the upstream it claims to be.

Oracle
Real upstream artifacts: the genuine xz release tarball against its genuine git tag
Invariant
No false negatives in the high buckets, and a false-positive rate low enough that a real finding stays visible
Honest limit
The compromised 5.6.1 tarball is unobtainable -- snapshot.debian.org carries only 5.6.1+really5.4.5-1, Debian's revert -- so the fixtures reproduce the technique against a clean release: genuine macro, serial intact, one comment appended, no payload. Detection keys on provenance and never on recognising a payload, which is the only reason it generalises past this one incident. The README says exactly this.

jail

unprivileged Landlock sandbox 596 lines · 77 tests

Compiles a one-line policy into a Landlock ruleset and execs a command inside it. No root, no container, no seccomp -- just the kernel's own filesystem access control. The oracle is the kernel: denied means a real EACCES from a real program, not an assertion about my own data structures.

Oracle
The kernel. Every rule is checked by running a real program and reading its errno
Invariant
A path that was not granted is never reachable, and the child cannot relax its own sandbox
Proof
The escape probe tries to clear no_new_privs and is refused -- the flag is one-way by design. So it builds the most permissive ruleset it can express, READ_FILE on /, and calls restrict_self with it. That call succeeds, and changes nothing: domains only ever intersect, so a permissive domain on top of a restrictive one yields the restrictive one. The read is still EACCES.
Caught
Eight assertions, zero passing, on the oracle's first execution. The ruleset was built perfectly and applied to the wrong program -- the rule loop had reused the parse loop's index, so jail exec'd a rule instead of the command.

tarx

tar reader and writer 1,181 lines · 118 tests

Full ustar plus the pax extensions, both directions. Extraction is a classic path-traversal sink, so refusal is tested harder than extraction: 15 malicious archives, each asserting a nonzero exit, that nothing was written outside the destination, and that a canary string never appears in any output.

Oracle
GNU tar, bidirectional. It must read what we write and we must read what it writes
Invariant
GNU tar agrees both ways, and no member can ever be written outside the destination
Attacks
Traversal via .., absolute paths, the ustar prefix field, escaping symlink and hard-link targets, pax path= and GNU L smuggling, and a pre-existing symlink in the destination
Caught
setuid, setgid and sticky bits were being restored from an untrusted archive. GNU tar drops them unless root; we were not.
The pattern

The harness was usually the bug

Across this work the test rig was wrong far more often than the code was. Each of these suites was green while checking nothing, and each was found by deliberately breaking the thing it was supposed to catch.

inflate

The sanitizer build could not fail

Reject tests asserted exit code exactly 1. AddressSanitizer also exits 1. Deleting the classic dist > out bounds check left 146 tests passing while ASan printed a heap overflow to stderr. Fixing the exit code revealed that every malformed input had also been leaking 192KB, invisible for the same reason.

httpd

curl was rewriting the attack

curl 'http://h/%2e%2e/secret' normalises the escape away and actually sends GET /secret. Two traversal assertions were green for a request that was never made. --path-as-is is required -- and curl does not normalise when the separator is also encoded, so only some cases were affected.

sha2

The empty-input test cannot detect a broken length encoding

Sabotaging the bit-length field turned 54 checks red, but the standard short-message set still scored 1 of 65. The survivor is the empty message, because 0<<3 == 0<<2. The test everyone writes first is structurally incapable of catching that bug.

walkv

Four planted defects, one caught

The crash matrix crashed, recovered, verified and then stopped -- nothing ever wrote after a recovery, so a subtly wrong recovery was unobservable. Adding that one scenario took the suite from 83 to 163 cases and the defect now fails 20 of them.

pngc

The reference could not see half the data

The low byte of every 16-bit sample was untested by any oracle. Zeroing them left 71 checks green, because the reference decoder hands back 8-bit pixels and literally cannot represent what was under test.

Verify it

Every claim here is a command

None of this asks to be taken on trust. The numbers come from suites that run in seconds against tools already on your machine.

# srcdiff against the real xz artifacts
cd srcdiff && make test
  25 passed, 0 failed

# the Landlock escape attempt, against your own kernel
cd jail && make test
  77 passed, 0 failed

# GNU tar reads what we write, and 15 malicious archives are refused
cd tarx && make test
  118 passed, 0 failed

# and the harness mutation check: can the suite actually fail?
cd walkv && make mutants
  (no defect)      216 scenarios checked, 0 failed
  no-crc           caught (1 scenarios failed)
  truncate-cursor  caught (20 scenarios failed)
  accept-short     missed, as expected -- the klen check masks it: defense in depth
  no-fsync         missed, as expected -- only a device-level test can see this
  ack-before-sync  missed, as expected -- the same ceiling, from the other side

Those last three lines are the point. Killing a process does not lose the page cache, so no process-kill harness can test durability against real power loss -- however thorough it looks. Removing the fsync call entirely leaves every scenario green. That is asserted as a known miss rather than quietly left out, so the limit is a measured fact instead of a caveat.

There is more of this than is shown here, deliberately. Three projects I can defend line by line are worth more than a list, and a portfolio that needs a scrollbar is asking you to take its length as evidence.

Everything is C or standard-library Python. No frameworks, no dependencies beyond zlib. Every commit builds, verified by rebuilding each one from a clean checkout.
